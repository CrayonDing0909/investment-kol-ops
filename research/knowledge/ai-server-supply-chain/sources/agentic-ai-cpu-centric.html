Agentic AI Execution: CPU-Centric Perspective

這份 Georgia Tech / Intel paper 是 BusinessNext CPU explainer 背後的 primary research source。它可以支持「agentic AI 的某些工具型工作負載會把瓶頸推回 CPU」，但不能被寫成「所有 agentic AI 都有 88% latency 在 CPU」。

Why This Source Matters

BusinessNext 用這篇研究來解釋 CPU 為什麼在 agentic AI 時代重新重要。這個 HTML 頁把原始 paper 的數字拉回 context，避免把「特定 workload 的 up to 88%」誤寫成普遍現象。

Direct Quotes

“Agentic AI serving converts monolithic LLM-based inference to autonomous problem-solvers that can plan, call tools, perform reasoning, and adapt on the fly.”
“The majority of the external tools responsible for agentic capability, either run on or are orchestrated by the CPU.”
“Tool dominated agentic AI workloads are significantly bottle-necked by tool processing on the CPU consuming up to 88% of the end-to-end latency.”
“HP GPU system can shift the bottleneck from GPU to CPU when tool execution latency is comparable to LLM inference latency.”

Tutor Reading

這份 source 在解決什麼問題：當 LLM app 從單次 inference 變成多步驟 agent，瓶頸還是不是 GPU？paper 的答案是：很多工具執行、retrieval、code execution、orchestration 會落在 CPU 或 CPU-side workflow。

這份 source 可以支持的 claim：某些 tool-dominated agentic AI workloads 會出現高比例 CPU-side latency；高效 GPU 反而可能把 bottleneck 往 CPU 工具執行推。

不能直接公開寫的數字：不能把 up to 88% 寫成「agentic AI 88% latency 都在 CPU」。比較安全的寫法是「在 paper 測試的特定 tool-dominated workloads 中，CPU-side tool processing 最高可達 88% end-to-end latency」。

Reliability

  • primary research paper 適合支撐 CPU latency / bottleneck 的技術 claim。
  • do not overgeneralize 數字高度依賴 workload、system setup、tool mix，不能外推到所有 AI inference。
  • BusinessNext 的「CPU latency 過半」中文 framing 有方向性支撐，但公開寫法應引用原 paper 並附 workload context。

Follow-up

  • 公開文章要決定引用 arXiv URL 還是 Georgia Tech repository URL。
  • 如果用於投資 thesis，還要接回 AMD / Intel / server CPU demand 的 financial source，paper 本身不證明營收轉折。
  • 避免把 paper 的 optimization results 寫成商業產品已實現的效益。
